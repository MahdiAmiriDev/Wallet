# Wallet Payment Settlement, Refund, and Customer UI — مانع‌های اجرای یکپارچه

وضعیت: **اجرای مالی و فعال‌سازی UI انتخاب کیف پول در محدودهٔ فعلی ممکن نیست.** این نتیجه مربوط به قراردادهای حل‌نشده است، نه صرفاً نبود آزمون. گزارش‌های [تصمیم Mixed](Mixed-Wallet-Payment-Decision-and-Blockers.md) و [Gateهای HekmatOnline](HekmatOnline-Mixed-Payment-Go-No-Go-Gates.md) همچنان مبنا هستند. این بررسی هیچ نتیجهٔ درگاهی یا DB را قطعی فرض نمی‌کند.

| مانع | شاهد Source و ریسک | حداقل تصمیم/اطلاعات لازم |
|---|---|---|
| **بدهی Order پس از Capture صفر نمی‌شود** | `OrderService.CalcAmountForPayAsync` فقط مجموع Paymentهای Paid را از کل Order کم می‌کند؛ Wallet Capture را نمی‌خواند (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/OrderService.cs:412–448`). `PaymentService.GetOrderTotalPayment` نیز فقط Payment/RefundDetail را جمع می‌کند (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/PaymentService.cs:261–284`). برای `T=W+G` و `Payment.Total=G`، بدهی همین منطق پس از Capture برابر `W` می‌ماند. دستور فعلی تغییر منطق محاسبه قیمت را ممنوع کرده و `Complete` را به بدهی صفر با منطق موجود مشروط کرده است؛ این دو شرط با Mixed سازگار نیستند. | اجازه و قرارداد دقیق برای محاسبهٔ بدهی خالص با `GatewayPaid` و `WalletCapture - WalletRefund`، با حفظ قیمت‌گذاری و checkout عادی. بدون آن، `Complete` صحیح قابل اثبات نیست. |
| **درگاه نخست و سهم اقلام تأیید نشده‌اند** | HekmatOnline در `GenerateTokenAsync` هر بار Payment تازه می‌سازد و سپس Token می‌گیرد (`Modules/YashilPayment/YashilPayment.Infrastructure/ServiceImpl/HekmatOnlinePaymentGatewayService.cs:417–445`). Callback/Inquiry سفارش را پیش از Capture کامل می‌کنند (`:633–651، 759–773`) و نتیجهٔ نامعلوم را ممکن است `Unsuccessful` کنند (`:829–839`). هنگام Paid، `PaymentService.UpdatePaymentStatusAsync`، Procedure `[shp].[SetOrderItemPriceRightShare]` را فرا می‌خواند (`PaymentService.cs:119–125`؛ `Modules/YashilCommerce/YashilCommerce.Infrastructure/RepositoryImpl/OrderItemRepository.cs:417–420`). تعریف و رفتار Procedure برای `G<T` در Source موجود نیست؛ کاربر بررسی آن را به بعد موکول کرده است. | تأیید مکتوب مالک درگاه برای پرداخت جزئی، finality و Inquiry/Retry؛ تأیید مالک DB/مالی برای Procedure با `Payment.Total=G`. پس از آن می‌توان شاخهٔ Mixed را از ساخت Payment دوم جدا کرد و ترتیب Paid/Capture/debt/Complete را تغییر داد. |
| **آماده‌سازی فعلی تلاش Mixed قابل استفاده نیست** | `WalletOrderPreparationService.PrepareAsync` کلید را از Order می‌سازد و `ReserveAsync` را بدون `PaymentId` می‌خواند (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/WalletOrderPreparationService.cs:64–69، 136–150`)، ولی Reserve، `PaymentId > 0` و Payment موجود می‌خواهد و کلید واقعی را Payment محور می‌سازد (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/WalletReservationService.cs:33–63`). همچنین `Math.Min(T, available)` می‌تواند `W=T` تولید کند (`WalletOrderPreparationService.cs:129–135`)، خارج از scope Mixed. | پس از رفع دو مانع بالا، یک تلاش با کلید پایدار و تراکنش مشترک برای Paymentِ `G`، Reservationِ `W` و مانده‌ها؛ Replay و رقابت هم‌زمان باید با همان تلاش آزموده شوند. این مورد نیازمند تصمیم Schema نیست، ولی کد فعلی آن را انجام نمی‌دهد. |
| **Refund ترکیبی هنوز قرارداد اجرایی ندارد** | `ModifiedOrderItemService.AddRefundAsync` ابتدا `AddWalletRefundDetail` را اجرا می‌کند و سپس درگاه‌ها را تخصیص می‌دهد (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/ModifiedOrderItemService.cs:509–565`). آن شاخهٔ `Wallet` مربوط به Payment و اقساط قدیمی ناجا است، نه `WalletTransaction`/Capture مربوط به WalletProgram (`:597–633`). `WalletRefundService.RefundAsync` می‌تواند اعتبار Capture معتبر را در Ledger با سقف و کلید تکرار برگرداند (`Modules/YashilCommerce/YashilCommerce.Infrastructure/ServiceImpl/WalletRefundService.cs:31–74، 82–160`)، اما مبلغ سهم Wallet از اصلاح Order و finality بازگشت وجه درگاه هنوز به آن متصل نیست. `RefundDetail.Done` طبق سند تصمیم اثبات واریز نیست. اتصال خودکار، خطر بازپرداخت یا کسر دوباره دارد. | مسئول مالی/Refund، رویداد قطعی بازگشت پول درگاه و نگاشت gateway-first به اصلاح/لغو Order را تأیید کند؛ سپس فقط سهم Capture مرتبط به Ledger Wallet برگردد. |
| **UI انتخاب کیف پول مبلغ معتبر برای ادامه ندارد** | خلاصهٔ پرداخت MVC، `SumTotalForPay` و انتخاب درگاه را نشان می‌دهد (`Yashil.WebHost/Views/Order/_OrderSummaryForPay.cshtml`)؛ آماده‌سازی Wallet بالا نمی‌تواند Reservation معتبرِ متصل به Payment بسازد. نمایش `W/G` به‌عنوان مبلغ عملیاتی یا فعال‌کردن انتخاب Wallet، کاربر را به مسیری می‌برد که پرداخت قطعی و `Complete` صحیح ندارد. | پس از قرارداد بدهی/درگاه و آماده‌سازی اتمیک، endpoint پیش‌نمایش واجد شرایط، انتخاب Program و تاریخچهٔ دارای تفکیک Wallet/درگاه به مسیر MVC متصل شود. دادهٔ UI فقط نمایش است و مبلغ نهایی سمت سرور اعتبارسنجی شود. |

**تصمیم اجرایی فعلی:** هیچ تغییر مالی یا UI درگاه انجام نشد. افزودن مسیر Settlement یا UI انتخاب Wallet پیش از رفع مانع‌ها، قابلیت ناقص و از نظر مالی مبهم ایجاد می‌کند. کار مستقل بعدی با کمترین وابستگی، تأیید قرارداد بدهی و Procedure و پاسخ مالک HekmatOnline است؛ سپس می‌توان در یک تغییر منسجم آماده‌سازی، Callback/Inquiry، Refund و UI را پیاده‌سازی و آزمود.

**Verification:** Build/Test اجرا نشد، چون هیچ کدی تغییر نکرد. `project.assets.json` برای `YashilCommerce.Infrastructure` و `YashilPayment.Infrastructure` در محیط فعلی موجود نیست؛ موفقیت Build یا Runtime ادعا نمی‌شود.
